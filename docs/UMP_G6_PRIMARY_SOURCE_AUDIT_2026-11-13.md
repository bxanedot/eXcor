# Permissive SABR/UMP source recheck — 2026-11-13

**Decision: G6 remains blocked at 0/20.** A newly reviewed MIT-licensed implementation supplies a much fuller working model than the earlier partial schemas. It does not meet eXcor’s existing re-entry gate because its evidence is implementation plus synthetic tests, not an independently validated service contract and authorized decode-and-seek result.

## Eligibility and scope

I checked each repository’s license at the exact commit before reading project material:

- [LuanRT/YouTube.js, commit `204715b6acfb063dc306d8677e36fdbf09f293c5`, LICENSE](https://github.com/LuanRT/YouTube.js/blob/204715b6acfb063dc306d8677e36fdbf09f293c5/LICENSE): MIT.
- [LuanRT/googlevideo, commit `c0e73b283310c771cddc5af8993f0e6b55a7578e`, LICENSE](https://github.com/LuanRT/googlevideo/blob/c0e73b283310c771cddc5af8993f0e6b55a7578e/LICENSE): MIT.

I reviewed only these repositories’ first-party docs, source, examples and tests, plus the [official YouTube APIs catalog](https://developers.google.com/youtube/apis) and [IFrame Player API reference](https://developers.google.com/youtube/iframe_api_reference). GoogleVideo is an unofficial implementation project, not a Google specification. The source facts below describe that project; claims about YouTube’s server behavior remain inferences. No implementation or schema was copied, no live YouTube request was made, and no media body, signed URL, cookie or token was retained. This is a bounded source review, not a claim that no other public or private material exists.

## What the new source adds

YouTube.js’ SABR option generates manifest entries that identify audio/video formats by itag and xtags; its browser example delegates request and UMP handling to GoogleVideo. The YouTube.js browser README explicitly calls that example outdated, so it is a lead rather than independent validation. ([option and manifest mapping](https://github.com/LuanRT/YouTube.js/blob/204715b6acfb063dc306d8677e36fdbf09f293c5/src/types/StreamingInfoOptions.ts#L44-L46), [outdated example notice](https://github.com/LuanRT/YouTube.js/blob/204715b6acfb063dc306d8677e36fdbf09f293c5/examples/browser/README.md#L1-L4))

GoogleVideo’s TV-client `/initplayback` example shows a bootstrap path: obtain a TV client configuration, construct and encrypt an embedded player request, wrap it with streamer context, request an initplayback service URL, then parse Onesie headers/data and extract the player response. It avoids committing a reusable capture, but the example is not a protocol specification and does not demonstrate that every field is required or stable. ([example](https://github.com/LuanRT/googlevideo/blob/c0e73b283310c771cddc5af8993f0e6b55a7578e/examples/onesie-request/main.ts#L32-L240))

The streaming sources make the SABR request envelope substantially more concrete: they build a protobuf ABR request from client time/state, selected audio/video format IDs, initialization formats, buffered ranges, streamer configuration and context, then post it to the configured server ABR endpoint and expect UMP. The adapter also models player-driven format selection and buffer updates. This describes the reviewed client’s request construction; some message fields remain explicitly unknown in its proto definitions, and its adapter comments describe a shortcut that sets player time to a desired segment start instead of reproducing the player’s buffering policy. ([request construction](https://github.com/LuanRT/googlevideo/blob/c0e73b283310c771cddc5af8993f0e6b55a7578e/src/core/SabrStreamingAdapter.ts#L202-L390), [ABR request schema](https://github.com/LuanRT/googlevideo/blob/c0e73b283310c771cddc5af8993f0e6b55a7578e/protos/video_streaming/video_playback_abr_request.proto))

The code describes a useful UMP state model: media headers identify format, header ID, segment number, time and declared length; media chunks attach by header ID; media-end closes a segment; initialization metadata supplies track bounds; request-policy, context, protection, redirect, reload and error parts update the next request or stream state. `SabrSeek` is handled as a server-directed time update. These are source-level behaviors, not independently established server guarantees. ([part handling](https://github.com/LuanRT/googlevideo/blob/c0e73b283310c771cddc5af8993f0e6b55a7578e/src/core/SabrStream.ts#L595-L850), [segment buffering](https://github.com/LuanRT/googlevideo/blob/c0e73b283310c771cddc5af8993f0e6b55a7578e/src/utils/SabrSegmentBuffer.ts#L35-L100), [seek fields](https://github.com/LuanRT/googlevideo/blob/c0e73b283310c771cddc5af8993f0e6b55a7578e/protos/video_streaming/sabr_seek.proto))

## Remaining gate gaps

| Re-entry area | Evidence from this review | Status |
|---|---|---|
| Bootstrap and request shape | The example and ABR source provide a concrete client model, but are unofficial and leave fields or stability assumptions unresolved. ([bootstrap example](https://github.com/LuanRT/googlevideo/blob/c0e73b283310c771cddc5af8993f0e6b55a7578e/examples/onesie-request/main.ts#L32-L240), [ABR request](https://github.com/LuanRT/googlevideo/blob/c0e73b283310c771cddc5af8993f0e6b55a7578e/src/core/SabrStreamingAdapter.ts#L202-L390)) | Partial |
| ABR and representation choice | Local format choice, client state, buffered ranges and selected IDs are represented. No independent server selection policy or verified behavior is supplied. ([format/request handling](https://github.com/LuanRT/googlevideo/blob/c0e73b283310c771cddc5af8993f0e6b55a7578e/src/core/SabrStreamingAdapter.ts#L202-L390), [format choice](https://github.com/LuanRT/googlevideo/blob/c0e73b283310c771cddc5af8993f0e6b55a7578e/src/core/SabrStream.ts#L279-L310)) | Partial |
| UMP boundaries, ordering and completion | The reader handles byte-chunk fragmentation; stream code creates a reader per HTTP response. I found no response-boundary continuation assembler or test, and no tests for missing/out-of-order segments. Segment and VOD completion are modeled in code. ([reader](https://github.com/LuanRT/googlevideo/blob/c0e73b283310c771cddc5af8993f0e6b55a7578e/src/core/UmpReader.ts#L20-L95), [segment handling](https://github.com/LuanRT/googlevideo/blob/c0e73b283310c771cddc5af8993f0e6b55a7578e/src/core/SabrStream.ts#L595-L850), [tests](https://github.com/LuanRT/googlevideo/blob/c0e73b283310c771cddc5af8993f0e6b55a7578e/tests/ump.reader.test.ts)) | Partial |
| Seek mapping | Requests carry player time, and server `SabrSeek` can update it. The sources do not establish a general time-to-segment mapping rule; the stream tests do not exercise seek mapping. ([request/seek handling](https://github.com/LuanRT/googlevideo/blob/c0e73b283310c771cddc5af8993f0e6b55a7578e/src/core/SabrStream.ts#L339-L392), [seek schema](https://github.com/LuanRT/googlevideo/blob/c0e73b283310c771cddc5af8993f0e6b55a7578e/protos/video_streaming/sabr_seek.proto), [stream tests](https://github.com/LuanRT/googlevideo/blob/c0e73b283310c771cddc5af8993f0e6b55a7578e/tests/sabr.stream.test.ts)) | Not met |
| Errors, cancellation, redirects and session | Source/tests cover abort, retries, HTTP/SABR errors and attestation states. Redirect URLs are followed or installed without the fail-closed host policy eXcor requires. Token, client and playback-cookie context is modeled, but complete cookie/session-change behavior is not. ([stream lifecycle and redirects](https://github.com/LuanRT/googlevideo/blob/c0e73b283310c771cddc5af8993f0e6b55a7578e/src/core/SabrStream.ts#L208-L272), [request context](https://github.com/LuanRT/googlevideo/blob/c0e73b283310c771cddc5af8993f0e6b55a7578e/src/core/SabrStream.ts#L918-L1020), [tests](https://github.com/LuanRT/googlevideo/blob/c0e73b283310c771cddc5af8993f0e6b55a7578e/tests/sabr.stream.test.ts)) | Partial |
| Test vectors and bounds | Tests construct UMP responses with an in-process mock fetch and synthetic filled payloads; reader tests cover partial byte chunks. They are not captured service exchanges. The reader has no visible per-part size cap, and segment bytes accumulate until media-end, so the required hard bounds are not established. ([reader tests](https://github.com/LuanRT/googlevideo/blob/c0e73b283310c771cddc5af8993f0e6b55a7578e/tests/ump.reader.test.ts), [mock SABR tests](https://github.com/LuanRT/googlevideo/blob/c0e73b283310c771cddc5af8993f0e6b55a7578e/tests/sabr.stream.test.ts), [reader and segment buffer](https://github.com/LuanRT/googlevideo/blob/c0e73b283310c771cddc5af8993f0e6b55a7578e/src/core/UmpReader.ts)) | Partial |
| Authorized decode and seek | The repository includes a runnable Shaka example, but no recorded authorized media decode or mid-stream seek result. eXcor’s [playback evidence matrix](PLAYBACK_EVIDENCE_MATRIX.md) likewise has no qualifying SABR result. ([example README](https://github.com/LuanRT/googlevideo/blob/c0e73b283310c771cddc5af8993f0e6b55a7578e/examples/sabr-shaka-example/README.md)) | Not met |

The official YouTube pages checked describe the embedded player and its user-facing seek controls, not raw viewer-media bootstrap, ABR, UMP or segment assembly. That conclusion is limited to those pages and is an inference from their documented scope.

## Result

The MIT source is enough to improve the research baseline and plan a clean-room offline transport proof. It does **not** satisfy the existing [G6 re-entry criteria](UMP_FRAMING_RESEARCH.md#reopen-criteria-for-option-b): response-continuation and seek semantics remain unverified, required fail-closed limits are not demonstrated, and no owner-authorized full decode plus mid-stream seek is recorded. Keep G6 **BLOCKED / 0 of 20**; do not treat this source review or its mock tests as YouTube interoperability evidence.
